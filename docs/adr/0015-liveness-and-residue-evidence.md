# ADR-0015：活性保护与"无残留"的证据形式（交付后加固轮）

状态：已接受（2026-02-14，加固轮）｜决策者：无人值守自主决策

## 决策 1：`activate()` 必须有超时 —— 这是**活性**问题，不是性能问题

`PluginHost.#activate` 原本是 `await loaded.plugin.activate(ctx)`，**没有**上限。

由于所有生命周期操作共用一条**串行队列**（ADR-0007 决策 6），一个永不 resolve 的 `activate`
会造成：队列永久卡住 → 后续所有操作（**包括卸载这个插件本身**）都排在它后面 →
宿主再也回不来。这不是"某个插件坏了"，而是**整个宿主失去响应**，且用户没有任何自救手段
（唯一出路是重载窗口）。

现在：默认 15s 上限（`vscordis.activationTimeoutMs`），超时后**先发 `AbortSignal` 再回滚**。

两个细节值得写下来：

- **先 abort 再回滚**：回滚只清理宿主侧状态；插件侧那个还在跑的异步任务必须被叫停，
  否则"卸载完成"是假的。信号是唯一的沟通手段（我们无法强制终止同进程里的 Promise）。
- **超时不是用来催快的**：有专门的测试验证"慢但没超时"的插件正常激活。
  15s 这个默认值刻意给得宽松 —— 插件的激活确实可能发网络请求或读大文件。

## 决策 2：`void promise` 是未处理 rejection 的温床

修了两处：

- `PluginHost.#handleServiceChange` 里 `void this.#enqueue(...)`；
- `Runtime` 的 `onPlan: (plan) => { void this.#handleReloadPlan(plan) }`。

`void` 只丢弃返回值，不处理拒绝。这两处一旦抛出，Node 会报未处理的 rejection，
而调用方（注册表事件 / 文件监听）根本无从感知 —— 表现为"日志里有条警告，功能静默失效"。
两处都改成显式 `.catch()` 并记日志。

## 决策 3：「无残留」用**结构性断言**证明，内存只做趋势观察

这是本轮最重要的方法论选择。**结构断言是确定性的、可复现的**；内存断言在没有 GC 的前提下
根本不可靠（V8 的分配策略会让数字在几 MB 到几十 MB 之间随机漂移）。

四类证据：

| 场景 | 断言 |
| --- | --- |
| 200 轮「加载 3 个插件（A→B→C 依赖链）→ 全部卸载」 | **每轮**都断言：插件记录为空、`registry.size === 0`、命令表为空、该轮每个 incarnation 的副作用栈 `closed && size === 0`、模块释放数 = 轮数 × 3 |
| 50 次 reload 同一插件 | 51 个**互不相同**的模块实例（若 `require.cache` 没清干净，incarnation 会重复出现） |
| 20 轮起停**真实子进程** | `activeSessions === 0`（新增诊断），且每轮反向调用都拿到 `pong` |
| 200 轮的内存趋势 | 只做**宽松上界**（增长 < 60MB）并打印实测值，不做精确断言 |

为什么每轮都断言而不是只在收尾看一眼：级联路径（B 暂停时回收 `provide`，牵动 C）
是最容易留下残影的地方，只在最后看一次的话，中间某轮泄漏的槽位会被后续轮次掩盖。

实测值（未 GC，仅供参考）：200 轮 × 3 插件后 `heapUsed` 增长约 **6–7 MB**。

## 决策 4：把隔离会话数暴露到状态面板

`IsolatedPluginLoader.activeSessions` 不只在测试里用，也进 `vscordis: 显示运行时状态`。

理由：**诊断能力不该只活在测试里**。"当前有几个隔离子进程"是用户能自己判断
"卸载到底生效没有"的最直接指标，比让用户去任务管理器数 `node.exe` 靠谱。

## 后续轮次补齐：整栈回收总时长预算（原「已知缺口 1」）

单项超时有界 **≠** 卸载耗时有界：50 个挂死 teardown × 2s = 100s，而生命周期共用一条串行队列 ——
期间整个宿主无响应。所以加预算，但把"少回收"的代价显式化：

- `EffectStackOptions.disposeBudgetMs`：整栈总预算；`undefined` / `<= 0` = 不启用（与从前完全一致）；
- 预算在**项与项之间**检查：`remaining <= 0` 的项**不再执行**，逐项经 `onError` 上报
  （含 label 与"预算耗尽"字样，可检索）；未耗尽的项其单项超时取 `min(单项超时, remaining)`，下界 1ms；
- 栈仍然 `closed === true`、`size === 0`；新增只读诊断 `skippedByBudget`（计数，供测试与状态面板）；
- 跳过是**刻意**的取舍（本文档原本就写过"加预算就意味着有些 effect 一个回合都不给"）：
  宁可少回收几项并留下可检索记录，也不让宿主长时间回不来。
- 边界：**同步 teardown 无法被预算打断**（预算只在项与项之间检查）；单个同步长任务仍可超预算。

接线（不做就是又一个"声明了不生效"）：

- `PluginHostOptions.disposeBudgetMs` → 每个插件的 `EffectStack`；
- `activate` 消息新增 `disposeBudgetMs` → 隔离子进程里的 `EffectStack`（两种模式同一份配置值）；
- 宿主设置 `vscordis.disposeBudgetMs`，默认 **30000**，`0` = 显式关闭（回到旧行为）；
- 测试：kernel（`plugin-host.spec.ts`）与真实子进程（`isolation.spec.ts`）各一条 ——
  预算被挂死项吃光后，后续项被跳过、日志含 label 与"预算耗尽"、卸载耗时远小于单项超时 × N。

## 已知缺口

1. ~~`EffectStack.dispose()` 的总时长是 N × 单个超时~~ → 见上（已补预算与两种模式的接线）。
2. ~~内存断言依赖未 GC 的堆数据~~ → 已补**可选严格模式**（仍不是 CI 默认路径）：
   `node --expose-gc packages/kernel/test/soak.spec.ts` 跑 100 轮热身 + 1000 轮浸泡，
   清掉夹具记账后强制作 3 次 `gc()`，比较 `heapUsed`（阈值 0.8MB），并**同时**断言结构归零 ——
   否则"内存没涨"可能只是记账又没生效（ADR-0019 那个假绿的教训）。
   - 为什么不用 `node --expose-gc --test …`：V8 标志**不会**传给 test runner 的子进程，
     `global.gc` 是 undefined，用例会被静默跳过（实测过）。
   - **实测坑（值得写下来）**：不清夹具记账时，曲线是 ~4KB/轮的**线性增长**（3000 轮 +11MB）；
     清掉 `FakeHostPort.logs` / `moduleLoads` / `moduleReleases` 后是**平台期**
     （3000 轮稳定在 ~8.5MB，斜率趋 0）。原因是 `PluginHost` 每次状态转换都记一条 debug 日志，
     而夹具把日志留在数组里 —— 量内存时把夹具自己的记账留在里面，就会把**工具当成被测对象**。
   - 结论：在这个探针下**没有观察到运行时的线性泄漏**；严格用例的阈值（0.8MB / 1000 轮）
     用来抓"每轮 ≥1KB"级别的回归。
3. **超时后插件侧的异步工作是否真的停止，取决于它是否尊重 `ctx.signal`**。
   我们只能发信号，无法强制。这一点在 SDK 的 `PluginContext.signal` 注释里已写明。
4. 隔离浸泡只跑 20 轮（每次起进程约 45ms），不是 200 轮 —— 时间成本与收益的取舍。
