# ADR-0012：完整性与签名策略（M4a）

状态：已接受（2026-02-14，M4a 实施轮）｜决策者：无人值守自主决策

## 背景

用户决策：「开发模式（工作区插件）可未签名；装入 globalStorage 的插件必须签名 + 哈希校验」。
ADR-0008 已确定密钥存放与"签名放独立文件"以避免自引用。本 ADR 补齐策略与语义细节。

## 决策 1：校验发生在 `require` **之前**，且失败即拒绝加载

`NodeModuleLoader.load()` 的顺序固定为：路径 containment → **完整性/签名校验** → 清缓存 → `require`。
把校验放在 `require` 之后等于没校验（恶意代码已经被求值）。

失败抛 `PluginIntegrityError`（fail-closed），插件进入 `failed` 并暴露原因。

## 决策 2：签名覆盖「整个清单的规范化 JSON」，`integrity` 是清单的一部分

```
payload   = canonicalJson(manifest)          // 递归按 key 排序，与书写顺序无关
signature = ed25519_sign(payload)            // base64 → plugin.sig
integrity = { algorithm:'sha256', file: main, hash: sha256(file) }
```

要点是**两条防线各司其职**，缺一不可：

- 只有 `integrity` 时：能发现"产物被换"，但攻击者可以同步改写 `integrity.hash`（哈希谁都会算）；
- 加上签名后：改写清单就会破坏签名。测试
  `篡改产物并同步改写 integrity.hash：被签名抓住` 专门验证这条链路。

`canonicalJson` 是纯函数且被签名方与验签方**共用同一实现**（`signPluginDirectory` 与
`verifyPluginArtifact` 都在 `integrity.ts` 里），避免"脚本与校验器各写一套"的经典漂移。
有测试覆盖"重新排列 key 顺序后签名依然有效"。

## 决策 3：按来源分级，而不是按全局开关

| `source` | 策略 |
| --- | --- |
| `workspace` | 签名**可选**；但若存在签名，仍然严格校验（不允许"签了但签错"被放行） |
| `global` | 签名**必须**；缺 `plugin.sig` 直接拒绝，错误信息里给出 `docs/signing.md` |

理由：开发期反复重建产物，强制签名会让 `npm run watch` 与热重载寸步难行；
而"安装到本机"是一次性动作，强制签名几乎不增加成本，却能挡住供应链篡改。

## 决策 4：带签名但宿主没有公钥 → 拒绝，而不是跳过

看起来"没公钥就当作未签名放行"更宽容，但那会让攻击者只需删掉公钥文件就能降级整套机制。
所以选择 fail-closed，并在启动日志里明确提示公钥缺失。

## 决策 5：测试用临时密钥对，不依赖仓库里的私钥

`integrity.spec.ts` 在运行时 `generateKeyPairSync('ed25519')`，
于是 CI 上也能全量验证签名链路，且**私钥永不进入仓库或 CI**。

## 已知缺口（必须一起读）

1. **没有吊销机制**。换密钥 = 旧签名全废；没有"这把钥匙泄露了，作废它"的能力。
   要做到需要版本化信任根 + 公钥清单，列入后续工作。
2. **签名不构成沙箱**。它证明"代码是发布者的"，不证明"代码是善意的"。
   同进程插件仍可绕过受控 API（ADR-0003）。真正的边界是子进程（M4b）。
3. **`plugin.json` 会被签名脚本重写**（统一缩进）。这对格式化习惯不同的贡献者是个小摩擦，
   换来的是"清单字节级可复现"，值得。
4. **未做**：插件目录中除 `main` 之外文件的哈希（例如多文件插件的子模块）。
   当前只签入口产物 —— 这正好与"插件必须是单文件 CJS"（ADR-0009）这条约束自洽。
